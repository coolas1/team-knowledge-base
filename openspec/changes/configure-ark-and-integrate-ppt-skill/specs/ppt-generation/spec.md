## Purpose

Provide visually coherent image-based presentations by letting the existing chat Agent invoke a pinned skill against authorized sources, with bounded model usage and a trustworthy PPTX attachment returned in the same conversation.

## ADDED Requirements

### Requirement: PowerPoint requests use the image presentation skill
The chat Agent SHALL route every PPT or PowerPoint generation request to the image presentation skill while preserving existing DOCX and PDF generation. It MUST disclose that image-slide elements are not individually editable and SHALL NOT claim an outline file is an editable equivalent.

#### Scenario: Existing document tool is called
- **WHEN** the chat Agent uses the existing document generation tool
- **THEN** only DOCX and PDF formats are offered and their output behavior remains compatible

#### Scenario: A natural-language PPT request is routed
- **WHEN** a user asks for a PPT or PowerPoint without naming a tool
- **THEN** the Agent offers only the image presentation tool for that format

### Requirement: Presentation generation starts in the existing chat
The system SHALL let a user request an image-based presentation in the existing question-and-answer chat. The Agent MUST invoke the pinned codex-ppt skill and MUST NOT require navigation to a dedicated PPT page.

#### Scenario: User requests a presentation naturally
- **WHEN** an authorized user asks in chat to generate a PPT from the conversation or selected sources
- **THEN** the Agent invokes the PPT skill and reports its progress and result in that conversation

#### Scenario: PPT navigation is inspected
- **WHEN** the application navigation and client routes are rendered
- **THEN** no dedicated PPT page or PPT navigation entry is exposed

### Requirement: Clarification uses normal conversation
The PPT skill MAY request missing presentation constraints through an ordinary assistant message. The user's generation request SHALL authorize the resulting bounded tool execution; the system MUST NOT introduce a separate outline or sample approval state machine.

#### Scenario: Required input is missing
- **WHEN** the skill cannot determine a necessary title, audience, page count or source
- **THEN** the assistant requests that information in chat and invokes the skill after the user replies

### Requirement: Compatible generation backend and source assets
Slide visual backgrounds SHALL be generated by the configured image backend using validated capabilities, not placeholder screenshots. Exact titles and points SHALL be rasterized locally with a packaged CJK font before visual QA so Chinese and numeric fidelity do not depend on image-model typography. Required reference images MUST be composited locally without cropping or redrawing into versioned, recorded regions and supplied to final visual QA. Upstream skill origin, pinned version and workflow adaptations SHALL be recorded and available for review.

#### Scenario: Required image cannot be preserved
- **WHEN** an original figure cannot be read, fit without cropping, or verified in the final composite
- **THEN** that page is blocked with a specific reason rather than silently generated from text alone

#### Scenario: Reference regions are planned
- **WHEN** the skill plans a page containing required original assets
- **THEN** it records the server-calculated image regions and source checksums, and a region-policy change invalidates the affected page identity

#### Scenario: Final image is composed
- **WHEN** a generated background receives required reference assets
- **THEN** the system records original checksums and fitted pixel rectangles, verifies embedded pixels against aspect-preserving resized originals, and preserves the final PNG bytes inside the PPTX

### Requirement: Skill results use chat progress and attachments
The system SHALL expose generation progress through the existing chat tool-event protocol and SHALL publish a completed PPTX through the existing conversation attachment mechanism. It MUST NOT depend on PPT-specific job tables, workers, task APIs or status polling.

#### Scenario: Foreground generation is quiet
- **WHEN** image generation or visual QA produces no tool event for an extended interval
- **THEN** the chat stream sends SSE heartbeat comments so an idle transport does not cancel healthy work

#### Scenario: Generation succeeds
- **WHEN** the skill completes validation and assembly
- **THEN** the assistant message contains a real, authorized PPTX attachment that remains downloadable with the conversation

#### Scenario: Generation fails
- **WHEN** a provider, rendering or validation stage fails
- **THEN** the chat reports the failing stage and known usage without creating a hidden background retry

#### Scenario: Terminal generation failure is returned
- **WHEN** the foreground PPT tool exhausts its internal per-page attempts and returns a known failure
- **THEN** the Agent turn completes with that failure as a visible answer instead of emitting a generic agent-run failure or automatically invoking the whole deck again

### Requirement: Scope applies throughout presentation lifecycle
The system SHALL enforce trusted bank/tag permissions for source reads, reference assets, skill execution and attachment download. Credentials MUST remain server-side. Source or authorization changes SHALL prevent further unauthorized generation and access.

#### Scenario: Another bank requests an artifact
- **WHEN** a caller outside the conversation scope requests a source or generated artifact
- **THEN** access is denied without exposing private content

#### Scenario: Source permission is revoked
- **WHEN** an invocation loses access to a required source before reading or assembly
- **THEN** further generation is blocked and existing private materials are not served to the revoked caller

### Requirement: Bounded generation and cancellable work
The system SHALL bound page count, model attempts, repairs and concurrency within each skill invocation, include retries in accounting, and display unknown billing values explicitly. Failure or cancellation of the chat tool call SHALL prevent further model calls and final success publication while retaining known accounting.

#### Scenario: Budget is exhausted
- **WHEN** the next page would exceed the configured budget
- **THEN** the skill stops before that provider call and reports the budget condition in chat

#### Scenario: User cancels during generation
- **WHEN** an in-flight skill invocation is cancelled
- **THEN** no additional pages start and any late result cannot mark the task completed

### Requirement: Visual verification and artifact integrity
Each page SHALL pass structural and visual checks for content, readable text, numerical fidelity, required assets and style before assembly. The skill SHALL produce the expected page count, speaker notes and a valid PPTX, publish only verified attachment paths, and report failed-page reasons in chat.

#### Scenario: A page fails visual checks
- **WHEN** required text is missing or figures are incorrect
- **THEN** the page remains unaccepted and the deck is not reported as complete

#### Scenario: Mixed Chinese and Latin text is composed
- **WHEN** a locally rasterized title or point contains ordinary Latin technical terms
- **THEN** line wrapping preserves each term as a unit while keeping it within the assigned text region

#### Scenario: A comparison layout is requested
- **WHEN** a page requests a comparison or left-right layout
- **THEN** the final composition uses two visually distinct side-by-side panels and visual QA evaluates that structure

#### Scenario: Final download is offered
- **WHEN** a skill invocation is completed
- **THEN** the PPTX exists, opens with the expected slides and notes, and its download uses current authorization

### Requirement: Acceptance uses real bounded provider evidence
Before production enablement the workflow MUST pass a bounded synthetic deck test from the existing chat page, including natural-language routing, reference imagery, progress events and attachment download verification. Reports SHALL separate mocked fault tests from real provider outcomes and SHALL NOT infer image quality parity from transport success.

#### Scenario: Only mock generation has passed
- **WHEN** tests use placeholder provider results and no real Seedream output
- **THEN** end-to-end production acceptance remains incomplete

01 · EXECUTIVE CONCLUSION

核心结论：自动归档不是“File → LLM → Move”

多个真实项目的共同规律是：文件监听只负责发现事件；异步 Worker 负责耗时处理；内容理解层负责提取事实；规则和 AI 负责决策；Planner 生成操作计划；Validator 审核；Executor 最后才修改文件系统。

推荐总流程：

Watcher → Event Normalizer → File Stability → Job Queue → Extractor → Rule Engine → Candidate Retrieval → LLM/VLM → Action Plan → Validator → Executor → History / Undo

关键原则：LLM 不能直接操作文件系统，只能产生结构化决策。

03 · FOREL

Forel：最值得直接复刻的确定性架构

Forel 是开源 macOS 文件自动化工具。公开架构为 SwiftUI + ForelCore；Core 负责 Rule Engine、文件监听、SQLite persistence 和 Models。它使用原生 macOS FSEvents 监听目录。

Input ├── FSEvents：实时监听 ├── Run Now：手动处理 └── Dry Run：预览，不执行 ↓ Rule Engine ├── Scope Check ├── Condition Matching └── Plan Actions（conflict-aware） ↓ Action Executor ├── Move / Copy / Rename ├── Tag / Color ├── Trash / Delete └── Script ↓ History / Undo（SQLite）
核心设计：Plan Before Execute。
Dry Run、Manual Run、Watcher 三种入口共享同一个 plan(file)。只有最后一步决定是否 execute(plan)。

Forel 的内容匹配也很具体：纯文本直接读取；PDF 优先读取 text layer，空文本再 OCR；DOC/DOCX 使用系统 document reader；Office Open XML 可以 ZIP → XML → strip tags；图片使用本地 Vision OCR。

源码/资料：Forel GitHub

04 · HAZELNUT

Hazelnut：Watcher、Debounce 和 Rule Chain

Hazelnut 是 Rust 自动文件整理器，支持递归监控和 configurable debouncing；多个规则可以匹配同一个文件，并按顺序执行。

Filesystem Event ↓ Watcher ├── Recursive Watch ├── Debounce └── Normalize Path ↓ Rule Engine ↓ Rule #1 → Match? No ↓ ↓ Yes Rule #2 Execute Action ↓ Move / Copy / Rename / Archive / Trash / Script
重要启发：Watcher 不应该直接调用 AI。Watcher 是事件生产者；Rule Engine 是独立模块；Action 是独立抽象。这样后续增加 AI、Schedule、CLI 或 Web UI 都不会破坏核心逻辑。

源码/资料：Hazelnut GitHub

05 · PAPERLESS-NGX

Paperless-ngx：生产级系统为什么要使用任务队列？

Paperless-ngx 的 Consumer 监控 consumption folder，但 Consumer 本身不执行 OCR 等重任务，而是通知 Celery Task Processor。Message Broker 负责在 Consumer/Web/API 和 Worker 之间传递任务。

Consumption Folder ↓ Consumer ↓ Create Job ↓ Message Broker Redis / Valkey ↓ Celery Workers ↓ Document Processing ├── Type Detection ├── Parse / Convert ├── OCR ├── Metadata ├── Automatic Matching └── Search Index ↓ Database + Storage
为什么不能同步处理？
OCR、PDF 转换和索引都是慢任务，同步处理会阻塞新的文件事件。
Queue 的价值
并发 Worker、失败重试、任务状态、错误追踪和多个输入源统一处理。
最值得借鉴：Watcher/Consumer 只做 enqueue(job)，耗时处理全部放到 Worker。

资料：Paperless-ngx · Usage

06 · MINIMUM AI PIPELINE

最小 AI Organizer：watchdog → Extract → Ollama → Move

开源项目 pneelamr/ai-file-organizer 展示了最小 AI 自动归档链路：watchdog 监听新文件；PDF 用 PyPDF2 提取文本；图片用 Tesseract OCR；再通过本地 Ollama 分类。

New File ↓ watchdog ↓ File Type Router ├── PDF → PyPDF2 ├── Image → Tesseract OCR └── Other → metadata ↓ Ollama ↓ Category ↓ mkdir(category) ↓ move(file)
适合 MVP，但不适合生产。
缺少 file stability、persistent queue、structured output、candidate retrieval、path validation、collision handling、operation journal 和 undo。

源码：AI File Organizer

07 · MULTIMODAL AI

GenAI File Organizer：Extractor → VLM → Validator

这个项目公开了更完整的 AI Pipeline：支持 40+ 文件类型，本地 Ollama/llama.cpp，多模态内容理解，Watch Mode，History/Undo，以及 LLM-as-Judge 验证。

File Input（40+ types） ↓ Extractor Content / OCR / Media ↓ Categorizer（VLM） ↓ Namer（VLM） ↓ Validator（LLM-as-Judge） ↓ Rename / Organize ↓ History / Undo
建议借鉴“AI 输出后验证”，但不要每个文件都调用第二个 LLM。优先确定性 Validator；只有低置信度或高风险操作再走 AI Judge。

源码：GenAI File Organizer

08 · UNIFIED ARCHITECTURE

最终推荐的完整实现流程

① FILE DISCOVERY FSEvents / inotify / ReadDirectoryChangesW ↓ ② EVENT NORMALIZATION debounce · dedup · recursive · normalize ↓ ③ FILE STABILITY size stable? mtime stable? lock released? ↓ ④ PERSISTENT JOB QUEUE job status · retry · worker ↓ ⑤ FILE UNDERSTANDING metadata → parser → OCR → entities ↓ ⑥ DECISION Rules First → Retrieval → AI ↓ ⑦ ACTION PLAN MOVE / RENAME / TAG / ARCHIVE ↓ ⑧ SAFETY VALIDATION boundary · traversal · collision · permission ↓ EXECUTE → JOURNAL → INDEX UPDATE → UNDO
09 · STATE MACHINE

一个文件进入系统后的状态机

DISCOVERED ↓ DEBOUNCING ↓ WAITING_FOR_STABLE_WRITE ↓ QUEUED ↓ PROCESSING ├── metadata ├── text extraction ├── OCR └── entity extraction ↓ RULE_MATCHING ├── MATCHED → PLAN_READY └── UNMATCHED → RETRIEVE_CANDIDATES ↓ LLM_CLASSIFY ↓ PLAN_READY ↓ VALIDATING ↙ ↘ BLOCKED APPROVED ↓ EXECUTING ↓ COMMITTED ↓ INDEX_UPDATED Retryable Error → RETRY_WAIT → QUEUED Undo → UNDO_REQUESTED → REVERSE_EXECUTE
10 · FILE STABILITY

文件创建事件不代表文件已经写完

浏览器下载、网络复制、扫描仪输出都会出现：文件刚创建时系统已经通知 Watcher，但内容仍在写入。直接 OCR 或 move 会得到损坏文件。

on_event(path): debounce() repeat: previous = stat(path) sleep(500ms) current = stat(path) if size and mtime unchanged: stable_count += 1 else: stable_count = 0 if stable_count >= N: enqueue_job(path)
进一步建议：过滤 .crdownload、.part 等临时文件，检查文件锁，设置最大等待时间，并为失败任务设置 retry policy。
11 · FILE UNDERSTANDING

建立统一 FileContext，不要让后续模块理解各种文件格式

extract(file) → FileContext { file_id, path, name, extension, mime, size, created_at, modified_at, extracted_text, text_summary, metadata: { exif, pdf, office }, entities: [ {type, value, confidence} ] }
关键抽象：Rule Engine、Embedding Retrieval、LLM 全部只消费 FileContext。PDF/DOCX/JPG 的差异被封装在 Extraction Layer。
12 · DECISION ENGINE

Rules First + Candidate Retrieval + AI

FileContext ↓ Rule Engine ↓ Rule Match? YES ↓ ↓ NO Rule Plan Folder Retrieval ↓ Candidate Top-K ↓ AI Classification ↓ Structured Output ↓ Action Plan

Candidate Folder Retrieval

不要让 LLM 自由生成路径。先从 Workspace 现有目录检索 Top-K，再让模型选择 candidate_id。

Folders ├── Work/Research/LLM ├── Work/Research/CV ├── Finance/Invoices └── Personal/Reading Embedding(FileContext) ↓ Hybrid / Vector Retrieval ↓ Top-K Folder Candidates ↓ LLM: "只能选择 candidate_id， 或创建允许的子目录"
13 · LLM CONTRACT

LLM 输出必须是结构化决策

{ "decision": "MOVE", "folder_id": "folder_42", "new_name": "2026-03-ACME-Invoice.pdf", "confidence": 0.91, "requires_review": false }

后端负责将 folder_id 转成真实路径，并验证：

Schema Validation ↓ Folder exists? ↓ Workspace Boundary ↓ Path Normalize ↓ Collision Check ↓ Permission Check ↓ ActionPlan
14 · PLANNER & VALIDATOR

Planner 才是系统真正的安全边界

ActionPlan { plan_id, file_id, source_path, action_type, destination_dir_id, destination_path, rename_to, decision_source, confidence, validation_results, status }
Dry Run
只生成 ActionPlan，展示给用户。
Auto Run
ActionPlan → Validator → Executor。
15 · SAFETY

真正执行前必须检查的事情

检查解决的问题
Workspace Boundary禁止移动到系统目录或任意路径
Path Traversal处理 ../ 等路径逃逸
Collision目标已有同名文件
Permission没有读写权限
Fingerprint / Version处理中源文件发生变化
Loop Detection移动触发 Watcher 后再次处理
Delete Policy优先 Trash，而不是不可逆删除
16 · HISTORY & UNDO

Undo 应该建立在 Operation Journal 上

operations operation_id session_id file_id action_type source_path destination_path before_metadata after_metadata timestamp status undo_status

MOVE A → B 的 Undo 就是根据 journal 反向执行 MOVE B → A。复杂操作必须记录可逆信息，同时处理“用户已经修改目标文件”的冲突。

18 · DEVELOPMENT ROADMAP

建议的实现顺序

阶段实现目的
V0CLI + Rule Engine + Dry Run验证操作正确性
V1Watcher + debounce + stability + queue + history完成可靠自动化
V2PDF/DOCX/Image + OCR内容感知
V3Candidate Retrieval + Structured LLM OutputAI 自动归档
V4Entity Extraction + Folder Profile跨文件上下文
V5Knowledge Graph + Feedback Learning产品级智能化
最重要建议：不要一开始做 Knowledge Graph。先做可靠的 V1，再做内容理解 V2，最后接 AI V3。自动归档最难的问题首先是可靠性和安全性，其次才是 AI 智能程度。
19 · FINAL SYNTHESIS

最终应该从每个项目“拿什么”

Forel
Plan Before Execute、Dry Run、Conflict-aware Plan、Undo、多格式内容提取。
Hazelnut
Watcher 解耦、Recursive Watch、Debounce、Rule Chain、Action 抽象。
Paperless-ngx
Consumer/Worker 解耦、Queue、并行处理、失败任务。
Sortio
Rules First、AI Fallback、Entity Context、持续增量处理。
GenAI Organizer
多模态 Extractor、本地 VLM、AI Validation。
最终架构
可靠文件系统 + 内容理解 + 规则 + Retrieval + LLM Structured Decision + Transactional Execution。

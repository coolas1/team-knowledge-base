知识图谱解读

从问题出发，理解 GraphRAG 的核心模型、构建管线与主流架构

Part 1

知识图谱解决什么问题？

传统 RAG 把文档切成 chunk，用向量相似度检索。这在"答案就在某一个 chunk 里"时很好用，但遇到以下场景就力不从心：

📄

跨文档聚合

"王建国在所有文档里分别做了什么？"
答案分散在多个文档中，单次向量检索只能命中部分片段，无法给出完整画像。
🔗

关系多跳

"负责数据迁移的人，他的上级是谁？"
需要搜索两次：先找到负责数据迁移的人，再找到这个人的上级。向量检索无法做链式推理。
🌍

全局概括

"这些文档整体在讲什么事？有哪些主要主题？"
没有任何一个 chunk 能回答这个问题。需要对全部文档进行高度概括。GraphRAG 的做法：把实体聚类成"社区"，给每个社区写摘要，查询时匹配社区摘要。
🧩

实体消歧聚合

"王建国、王总、王经理分别做了什么？"
其实是同一个人，但纯 chunk 检索会把命中分散到不同片段。图谱通过实体对齐把别名合并为同一节点，一次查询即可聚合该人全部相关信息。
Part 2

核心模型

三元组 (Triple)

图的最小单元：(头实体, 关系, 尾实体)。例如 (张三, WORKS_AT, 万科物业)。

Schema 约束（预定义类型）

预定义的实体类型和关系类型，作为 LLM 抽取时的候选引导：

entity_types:
  core: [Person, Company, Building, Facility, Space, WorkOrder, Complaint, ...]

relation_types:
  core: [WORKS_AT, MANAGES, LOCATED_IN, BELONGS_TO, ASSIGNED_TO, ...]
术语澄清：Schema 约束 vs 本体 (Ontology) 这里更准确的叫法是"Schema 约束"而非严格意义上的"本体"。
Schema 约束：预定义 entity_types / relation_types 列表，作为 LLM 抽取时的候选引导，不具备形式化推理能力。（实际在用的）
本体 (Ontology)：带继承层级、基数约束、推理规则的形式化模型（OWL/RDF），支持自动推导隐含关系。（学术含义，暂未用到）

实例 (Instance)

实际的实体和关系数据：

{
  "entities": [
    {"name": "张三", "type": "Person", "description": "3栋业主"},
    {"name": "万科物业", "type": "Company", "description": "园区物业公司"}
  ],
  "relations": [
    {"from": "张三", "to": "万科物业", "type": "COMPLAINS_ABOUT", "desc": "投诉电梯故障"}
  ]
}

子图 & 社区

子图：完整图中的一块（如"3栋相关的所有实体和关系"）。
社区：紧密连接的节点簇，由聚类算法（如 Leiden）自动发现，代表一个主题领域。

实体/关系抽取

  • 实体抽取：使用 LLM，prompt 要求输出 JSON 格式，包含 name / type / description
  • 关系抽取：关系 = 两个实体之间的有向边。采用"预定义 + LLM 半开放自由发挥"的策略，既保证核心关系可控，又不遗漏长尾关系
  • 实体对齐：王建国 = 王总，识别为同一人，合并为一个节点
已知局限：同名消歧 当前对齐只处理"别名合并"（王建国 = 王总），尚未处理"同名消歧"（两个不同人都叫张伟，出现在不同文档中）。目前靠 LLM 抽取时附带的 description + type 字段做隐式区分，没有显式消歧模块。

图写入与后处理

  • Merge 语义：防止出现两个相同节点。先查找"张三"这个节点，没有的话再新建
  • 溯源：来源信息挂在 relation 上，每一个 relation 对应一个来源文档。文档更新时可精确清除对应边
  • 级联删除：文档删除后，清除其对应的 relation，再无连接的孤立实体节点一并删除
Part 4

主流架构对比

GraphRAG：分层聚合

核心思想：建立图的多层聚合，回答"整体讲什么"的问题。

Layer 3
全局摘要 —"整个语料库的主题"
↑ 聚合
Layer 2
社区摘要 —"数据中台相关的所有信息概括"
↑ 聚类（Leiden 算法）
Layer 1
实体 + 关系（基础图）
↑ 抽取
Layer 0
原始文本 chunks

LightRAG：双表索引

在 GraphRAG 基础上轻量化，建了两张索引表解决两类问题：

索引表解决的问题工作方式
实体表 简单局部问题
"张三负责什么？"		 命中"张三"这一行，顺带关联出"项目X"
关系表 抽象主题问题
"反映了什么技术决策和花钱情况？"		 拿"技术决策""花钱"等抽象主题词，在关系表的标签里匹配，找到对应关系和实体

核心差异

GraphRAGLightRAG
全局问题 社区摘要（Leiden 聚类 → LLM 生成） 关系表标签匹配（抽象主题词 → 关系 → 实体）
局部问题 实体邻域子图遍历 实体表行命中 → 顺带关联
构建代价 社区构建贵（O(n) 次 LLM 调用） 索引构建轻，但关系标签质量依赖抽取效果

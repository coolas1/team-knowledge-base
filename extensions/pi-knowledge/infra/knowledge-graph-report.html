1第一性原理：为什么需要知识图谱

从人类认知出发

人脑存储知识的方式不是"一段一段文本"，而是概念 + 关系的网络。当你想到"王建国"，你脑中浮现的不是某段文字，而是：

人脑中的"王建国"

王建国 → 是技术总监 → 在星辰科技 → 管理李明辉和张薇 → 负责数据中台项目 → 向陈志远汇报

这是一张网，不是一段文。

向量检索的根本局限

向量检索的本质是：把 query 和 chunk 都压缩成一个点，然后量距离。

能力向量检索知识图谱
找"语义相似"的文本擅长不适用
跨文档实体聚合受 top-K 限制，覆盖不全一次遍历全部关联文档
多跳推理（A→B→C）无法保证中间节点被召回沿边遍历，天然支持
全局概括（"整体讲什么"）不可能（只能看局部）社区摘要可回答
关系型问答（"谁管谁"）碰运气（取决于文本表述）直接查边
第一性原理总结

文本是知识的投影，图是知识的结构。向量检索在投影空间里找相似，知识图谱在结构空间里做遍历。两者互补，不替代。

2核心模型：图的结构与概念

属性图（Property Graph）

工业界主流模型。三个基本元素：

节点 Node 实体（人、组织、概念、文档）
边 Edge 关系（负责、属于、依赖、提及）
属性 Property 键值对（name="王建国", type="person"）
┌─────────────────────────────────────────────────────────────────┐ │ 属性图示例 │ │ │ │ (Doc:邮件.pdf)──MENTIONS──→(Entity:王建国 {type:person}) │ │ │ │ │ │ IN_DIR REL:管理 │ │ ↓ ↓ │ │ (Dir:test-dirty) (Entity:李明辉 {type:person}) │ │ │ │ │ REL:负责 │ │ ↓ │ │ (Entity:数据迁移 {type:project}) │ │ │ │ 节点有标签(Label)：Doc, Entity, Dir, Month │ │ 边有类型(Type)：MENTIONS, REL, IN_DIR, MODIFIED_IN │ │ 边可携带属性：REL {type:"管理", source_path:"会议记录.txt"} │ └─────────────────────────────────────────────────────────────────┘

关键概念

概念含义类比
Schema / Ontology图的"类型系统"：允许哪些节点类型、边类型数据库的 DDL
三元组 (Triple)(头实体, 关系, 尾实体) — 最小知识单元一行数据
本体 (Ontology)领域概念的形式化定义（"人可以有上级"）ER 图
实例 (Instance)具体数据（"王建国的上级是陈志远"）表中的一行
子图 (Subgraph)从完整图中切出的一块JOIN 查询结果
社区 (Community)紧密连接的节点簇（GraphRAG 核心概念）聚类结果

与关系数据库的本质区别

关系数据库

数据存在表里，关系靠 JOIN 临时计算。
3 跳 JOIN 性能指数下降。

图数据库

关系物理存储为指针。
遍历 N 跳 = 跟 N 次指针，O(1) 每跳。
天然适合"沿着关系走"的查询。

3构建管线：从原始文本到图

原始文档 ──→ 文本提取 ──→ 实体/关系抽取 ──→ 图写入 ──→ 后处理 (PDF/DOCX) (转换层) (LLM / NER) (Neo4j) (去重/合并)

Step 1: 实体抽取（NER / LLM）

传统 NER（命名实体识别）

用训练好的模型（BERT-NER、spaCy）标注文本中的人名、地名、组织名。
优点：快、便宜、确定性
缺点：只能识别预定义类型，无法抽取关系，无法理解上下文

LLM 抽取（你当前的方式）

把文本发给大模型，prompt 要求输出 JSON：{"entities":[...], "relations":[...]}
优点：零训练、可抽取任意关系、理解上下文
缺点：慢、贵、不确定性（同一文本两次抽取结果可能不同）

Step 2: 关系抽取

关系 = 两个实体之间的有向边。关键设计决策：

  • 关系类型是开放还是封闭？ 封闭（你当前：限定 person/org/project/tech/concept）vs 开放（任意动词短语）
  • 关系粒度："王建国管理李明辉" vs "王建国是李明辉的上级" — 同一事实，不同表述
  • 边属性：是否记录来源（哪个文档、哪个 chunk 产生的这条边）

Step 3: 实体对齐（Entity Resolution）

最难的环节

同一实体在不同文档中的不同写法：

文档 A文档 B实际是
王建国王总同一人
数据中台Data Platform同一项目
PostgreSQLPG同一技术

如果不做对齐，图中会出现重复节点，关系被割裂。
你当前的解决方式：维护任务中 LLM 调用 graph_merge_entities 手动合并。

Step 4: 图写入与后处理

  • MERGE 语义：存在则更新，不存在则创建（幂等）
  • 溯源：每条边记录 source_path，文档更新时可精确清除旧边
  • 孤儿回收：文档删除后，无连接的实体节点自动清理

4数据流动：构建期 vs 查询期

构建期（离线）

文档入库 ──→ graph_jobs 队列(pending) │ 维护任务触发（session_shutdown / 定时） │ ↓ 消费队列 ──→ 读文档全文 ──→ LLM 抽取 ──→ 写 Neo4j │ │ ↓ ↓ status = done Entity + MENTIONS + REL

查询期（在线）

用户 Query │ ├──→ BM25 检索 ──→ top-K chunks ──┐ │ │ ├──→ 向量检索 ──→ top-K chunks ──┤──→ RRF 融合 ──→ 排序结果 │ │ └──→ 图谱扩展 ─────────────────────┘ │ ↓ 取融合结果头部文档的实体 │ ↓ MATCH (Doc)-[:MENTIONS]->(Entity)<-[:MENTIONS]-(NeighborDoc) │ ↓ 邻居文档的 chunk 补充进结果（低权重）
关键设计约束
  • 图谱是纯派生索引：任何时候可以从源文档完全重建
  • 图谱不存储原文：只存实体名和关系类型，原文在 chunks 表
  • 查询时图谱只做补充，不做主路：主路是 BM25 + 向量

5主流架构对比

Microsoft GraphRAG（2024）

核心创新：社区摘要层
Layer 3: 全局摘要（"整个语料库的主题"） ↑ 聚合 Layer 2: 社区摘要（"数据中台相关的所有信息概括"） ↑ 聚类（Leiden 算法） Layer 1: 实体 + 关系（基础图） ↑ 抽取 Layer 0: 原始文本 chunks

查询流程：

  • Local Search：和传统 RAG 类似，从实体出发遍历邻居
  • Global Search：匹配社区摘要，回答"整体讲什么"类问题

代价：构建时需要对每个社区调用 LLM 生成摘要，成本高（O(社区数) 次 LLM 调用）

LightRAG（2024）

核心创新：双层检索
层级检索对象适合的问题
Low-level具体实体 + 直接邻居"王建国是谁？做了什么？"
High-level抽象概念 / 主题关键词"数据迁移涉及哪些技术？"

与 GraphRAG 区别：不做社区检测和摘要，而是把实体和关系分别建索引，查询时同时搜两层再融合。更轻量，但无法回答全局概括问题。

传统企业知识图谱（Google KG / Wikidata）

特点
  • Schema 严格预定义（不是 LLM 随意抽取）
  • 人工审核 + 众包编辑
  • 规模巨大（Wikidata: 1亿+ 三元组）
  • 查询语言：SPARQL / Cypher
  • 不依赖向量检索，纯图遍历

与 RAG 场景的区别：企业 KG 追求精确和完整；RAG 图谱追求"够用就行"，容忍噪声。

6边界与局限：什么不能做

知识图谱不擅长的

场景为什么不行该用什么
模糊语义匹配（"那个关于预算的事"）图遍历需要精确入口点向量检索
长文本理解 / 摘要图只存三元组，丢失上下文LLM 直接读原文
时序推理（"先做了什么后做了什么"）除非显式建时间边时间线索引
数值计算（"总预算多少"）图不存数值聚合结构化查询 / SQL
隐含知识（"他显然不高兴"）LLM 抽取只能提取显式陈述无法索引

构建期的根本挑战

  • 抽取质量上限 = LLM 能力上限。模型漏抽、错抽、幻觉都会污染图。
  • 实体对齐是 NP-hard 问题。没有完美方案，只有 trade-off（精度 vs 召回）。
  • 图会腐烂。文档更新后如果不清除旧边，图中会积累过时信息。
  • Schema 漂移。开放式关系抽取会导致关系类型爆炸（"负责""管理""领导""带"都是同一语义）。

查询期的根本挑战

  • 入口点问题：图遍历需要起点。如果 query 中的实体没被抽取过（或名字不同），图完全帮不上。
  • 深度 vs 精度：遍历越深，噪声越多。1-2 跳有用，3 跳以上通常全是噪声。
  • 与向量结果的融合权重：图补充的结果该给多少分？太高会引入噪声，太低等于没用。

你当前的定位

你的图谱是一个轻量级文档级实体索引，定位是向量检索的补充信号。 它不是 GraphRAG（没有社区/摘要），不是 LightRAG（没有双层检索），也不是传统企业 KG（没有严格 schema）。

在当前 8 篇文档、主题高度集中的场景下，这个定位是合理的。 当文档量增长到 100+ 且主题分散时，可以考虑的演进路径：

  1. 短期：过滤泛化实体（"星辰科技"），要求共享 2+ 实体才扩展
  2. 中期：实体链接下沉到 chunk 级（Entity → MENTIONED_IN → Chunk）
  3. 长期：引入社区检测（Leiden），为每个社区生成摘要，支持全局问题

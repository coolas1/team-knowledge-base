设计原则
  • 图谱是纯派生索引：任何时候可从源文档完全重建，不是 source of truth
  • 影子 Markdown 是系统内部语言：所有格式统一转为 md 再处理
  • 增量优先：文档级增量抽取，社区级定期全量
  • 三路互补：BM25 精确匹配 / 向量语义相似 / 图谱结构遍历

1. 存储层

1.1 摄取管线（端到端）

源文件（vault 目录）
    │
    ▼
格式转换 ──→ 影子 Markdown（.derived/ 目录）
    │              │
    │              ▼
    │         分块（chunkMarkdown）
    │              │
    │              ▼
    │         向量化（doubao-embedding-vision-251215, 1024d）
    │              │
    │              ▼
    │         写入 ParadeDB（documents + chunks 表）
    │              │
    │              ▼
    └────→ 写入 graph_jobs（status=pending）──→ 图谱构建（异步）

1.2 格式转换

源格式转换方式输出实现文件
PDFpdfjs-dist/legacy（含 CMap）逐页文本拼接convert/pdf.ts
DOCXmammoth（按段落）Markdown 段落convert/docx.ts

影子文件（.derived/）
  • 路径：D:\knowledge-vault\.derived\{相对路径}.md
  • 用途：缓存昂贵转换、给 agent 提供全文读取、调试窗口
  • Session 不生成影子文件（独立管线，直接入库）

1.3 分块策略

参数值含义
TARGET_CHARS800目标块大小（≈400-500 token）
MAX_CHARS1600硬上限，超过必切
MIN_CHARS100尾块小于此值并入前块

切分逻辑：按标题行切章节 → 章节内按空行切段落 → 贪心聚合到目标大小 → 超长硬切。代码围栏内不切。

1.4 数据库 Schema（ParadeDB / PostgreSQL）

-- 4 张表
documents (id, source_path UNIQUE, kind, title, content_hash, shadow_path,
           mtime_ms, meta JSONB, embedding_model, indexed_at)

chunks    (id, doc_id FK, seq, heading, content, asset_path,
           embedding vector(1024))

graph_jobs (doc_id FK, status, attempts, last_error, updated_at)

index_meta (key UNIQUE, value JSONB)

-- 2 个索引
BM25 全文索引: USING bm25 (id, content::pdb.jieba, heading::pdb.jieba)
HNSW 向量索引: USING hnsw (embedding vector_cosine_ops)

1.5 Session 摄取（增量尾部重做）

~/.pi/agent/sessions/*.jsonl
    │
    ▼
extractSessionText（只保留 user + assistant 文本）
    │
    ├── 首次：全量分块 → embed → 入库（meta.line_count = N）
    │
    └── 续聊（lines > meta.line_count）：
         取新增行 → 提取文本 → 合并最后旧 chunk → 重新分块
         → 删最后旧 chunk → 插入新 chunk → 更新 line_count
方案 C 优势

续聊时只重新 embed 尾部 1-2 个 chunk，前面的 chunk 不动。省 API 调用，保证分块边界正确。

2.3 实体链接粒度

抽取方式：文档级（全文送入 LLM，截断 8000 字）
链接方式：Doc ──MENTIONS {chunks: [0, 3, 7]}──→ Entity

含义：该文档的第 0、3、7 号 chunk 提到了此实体
查询时：可通过 chunks 属性精确定位到段落，无需二次搜索

2.4 构建流程

文档入库 ──→ graph_jobs (pending)
                  │
         维护任务 / session_shutdown 触发
                  │
                  ▼
         读文档全文（chunks 拼接，截断 8000 字）
                  │
                  ▼
         LLM 抽取（doubao-seed-2-0-lite）
         Prompt 要求输出：
         {
           "entities": [{"name", "type", "chunks": [0,3]}],
           "relations": [{"source", "target", "relation"}]
         }
                  │
                  ▼
         写入 Neo4j：
         - MERGE Entity 节点
         - MERGE Doc ──MENTIONS {chunks}──→ Entity
         - MERGE Entity ──REL {type, source_path}──→ Entity
                  │
                  ▼
         graph_jobs.status = 'done'

2.5 社区层（每日刷新）

每日维护任务：
    │
    ├── 1. Leiden 社区检测（Neo4j GDS 或 JS 实现）
    │       → 每个节点分配 community_id
    │
    ├── 2. 社区摘要生成
    │       → 每个社区：收集成员实体 + 关系 → LLM 生成 200 字摘要
    │       → 存入 Neo4j 节点 (Community {id, summary, member_count})
    │
    └── 3. 社区层级（可选）
            → 社区间的跨社区边 → 二级聚类 → 更高层摘要
成本估算（1000 篇文档）
  • 实体抽取：1000 次 LLM 调用（增量，分散在每次入库时）
  • 社区检测：纯算法，无 LLM 成本
  • 社区摘要：~50 个社区 × 1 次 LLM = 50 次/天
  • 实体对齐：~10 次/天（只处理新增冲突）

2.6 结构边（非语义）

边含义用途
Doc → IN_DIR → Dir目录层级按文件夹浏览/过滤
Doc → MODIFIED_IN → Month修改时间时序查询
Doc → DERIVED_FROM → Doc记忆派生自会话溯源

3. 检索层

3.1 三路并行架构

用户 Query: "负责数据迁移的人，他的上级是谁？"
    │
    ├──────────────────┬──────────────────┬──────────────────┐
    ▼                  ▼                  ▼                  │
┌────────┐      ┌────────────┐      ┌────────────┐         │
│  BM25  │      │   向量检索   │      │  图谱检索   │         │
│        │      │            │      │            │         │
│ jieba  │      │ embed(query)│      │ 实体匹配   │         │
│ 分词   │      │ cosine sim │      │ + 图遍历   │         │
│        │      │            │      │            │         │
│ top-20 │      │ top-20     │      │ top-N docs │         │
└───┬────┘      └─────┬──────┘      └─────┬──────┘         │
    │                  │                    │                │
    └──────────────────┴────────────────────┘                │
                       │                                     │
                       ▼                                     │
              ┌─────────────────┐                            │
              │   RRF 融合       │                            │
              │ score = Σ 1/(60+rank) │                       │
              └────────┬────────┘                            │
                       │                                     │
                       ▼                                     │
              ┌─────────────────┐                            │
              │  全局问题路由     │←── 社区摘要匹配            │
              │  (可选第四路)    │                            │
              └────────┬────────┘                            │
                       │                                     │
                       ▼                                     │
                  最终排序结果 ──→ 返回给 pi-agent            │

3.2 各路细节

BM25 路
  • 引擎：ParadeDB BM25 索引
  • 分词：jieba（中文）
  • 查询：content ||| '词1 词2'
  • 评分：pdb.score()
  • 返回：top-20 chunks
向量路
  • 模型：doubao-embedding-vision-251215
  • 维度：1024
  • 距离：cosine
  • 索引：HNSW
  • 返回：top-20 chunks
图谱路 重设计
  • 入口：query → jieba → 匹配 Entity.name
  • 遍历：1-2 跳邻居
  • 返回：关联文档的 chunks（通过 MENTIONS.chunks 定位）
  • 全局：匹配 Community.summary

3.3 图谱检索路径（新设计）

Query: "王建国和李明辉什么关系？"
    │
    ▼
jieba 分词: ["王建国", "李明辉", "关系"]
    │
    ▼
实体匹配: MATCH (e:Entity) WHERE e.name IN ["王建国", "李明辉"]
    │
    ▼
关系查询: MATCH (a)-[r:REL]->(b) WHERE a.name="王建国" AND b.name="李明辉"
    │
    ▼
命中: (王建国)-[:REL {type:"管理"}]->(李明辉)
    │
    ▼
溯源: r.source_path → 找到来源文档 → 返回对应 chunks

Query: "这些文档整体在讲什么？"（全局问题）
    │
    ▼
意图判断: 无具体实体 / 含"整体""概括""所有"等关键词
    │
    ▼
社区摘要匹配: MATCH (c:Community) RETURN c.summary
    │
    ▼
返回: 所有社区摘要拼接（或 top-N 相关社区）

3.4 RRF 融合

Reciprocal Rank Fusion

fused_score(chunk) = Σ 1 / (K + rank_in_path)，K = 60

  • 同一 chunk 被多路命中 → 分数叠加 → 排名靠前
  • 不依赖各路原始分数的可比性
  • 图谱路补充的结果：使用 fusedFloor × 0.9 作为保底分

3.5 过滤与降噪

  • 泛化实体黑名单：公司名（"星辰科技"）不作为图谱扩展依据
  • 共享实体阈值：邻居文档需共享 ≥2 个实体才补充（避免单实体噪声）
  • kind 过滤：session 类文档永不注入上下文（仅供检索兜底）

4. 维护层

4.1 触发机制

触发点执行内容
session_shutdownvault 增量扫描 + session 摄取 + graph_jobs 消费
每日定时社区检测 + 摘要刷新 + 实体对齐 + 关系归一化
手动（工具调用）全量重建 / 单文档重建 / 健康检查

4.2 维护任务清单

maintain() 执行顺序：
    │
    ├── 1. vault 增量扫描
    │       新增/修改 → 转换 → 分块 → embed → 入库 → graph_jobs
    │       删除 → 清理 documents + chunks + Neo4j 派生边
    │
    ├── 2. Session 摄取
    │       扫描 ~/.pi/agent/sessions/ → 增量尾部重做
    │       消失的 session → 清理
    │
    ├── 3. 图谱构建（消费 graph_jobs）
    │       pending → LLM 抽取 → 写 Neo4j → done
    │       失败重试（最多 3 次）
    │
    ├── 4. 实体对齐（LLM 辅助）
    │       找出疑似重复实体 → graph_merge_entities
    │
    ├── 5. 关系归一化 新增
    │       找出语义重复的关系类型 → 合并为推荐列表中的标准类型
    │
    ├── 6. 社区检测 + 摘要（每日）新增
    │       Leiden → 社区摘要 → 存入 Neo4j
    │
    ├── 7. 孤儿回收
    │       无连接的 Entity / Dir / Month 节点删除
    │
    └── 8. 记忆提炼（可选）
            会话 → LLM 提炼 → memories/ 目录 → 入库

4.3 实体对齐策略

维护时 LLM 辅助合并
  1. 找出疑似重复：名称编辑距离 < 3，或一个包含另一个（"王建国" vs "王总"）
  2. LLM 判断：给出两个实体各自出现的文档列表，问"是否同一实体？"
  3. 合并：保留最完整名称，MERGE 所有边到目标节点，删除源节点

工具：graph_entity_docs（查文档）+ graph_merge_entities（执行合并）

4.4 图谱重建保障

幂等性设计
  • 每条语义边携带 source_path → 文档更新时精确清除旧边再重建
  • MERGE 语义（存在则更新）→ 重复执行不产生重复数据
  • 全量重建：清空 Neo4j → 所有 documents 重新入 graph_jobs → 消费
